# PRD 撰写技能

## 描述
根据用户提供的需求要点，自动生成符合团队规范的 PRD 初稿，覆盖完整的需求定义、功能设计、交互说明和验收标准，可直接用于团队评审。

## 使用场景
- 用户要求写 PRD 或产品需求文档
- 用户描述了一个功能需求，需要转化为规范文档
- 用户提到"PRD""需求文档""功能说明""需求规格"等关键词
- 产品评审前需要输出规范的需求文档

## 指令

### 第一步：需求澄清
1. 仔细阅读用户提供的需求描述
2. 如信息不完整，向用户追问以下关键信息（不要一次性问太多，最多问 3 个最关键的）：
   - 这个功能要解决什么用户问题？
   - 目标用户是谁？
   - 有没有参考产品？
   - 有没有时间约束或技术约束？
3. 如信息足够，直接进入第二步

### 第二步：PRD 文档结构

按以下结构输出 PRD，每个模块不可省略：

#### 1. 文档信息
| 字段 | 内容 |
|------|------|
| 需求名称 | xxx |
| 需求编号 | 自动生成（如 PRD-2026-001） |
| 编写人 | （用户） |
| 优先级 | P0/P1/P2 |
| 预计上线时间 | xxx |

#### 2. 需求背景
- 为什么要做这个需求（业务背景或用户痛点）
- 市场或竞品参考
- 预期收益（量化指标，如转化率提升 X%）

#### 3. 需求目标
- 核心目标（1-3 个，必须可衡量）
- 非目标（明确这个需求不做什么，防止范围蔓延）

#### 4. 用户故事
- 格式：作为【角色】，我希望【功能】，以便【价值】
- 至少 3 个用户故事，覆盖主要场景

#### 5. 功能设计
- 功能清单（表格形式，含优先级）
- 每个功能的详细说明：
  - 功能描述
  - 输入/输出
  - 业务规则
  - 异常处理
  - 状态流转（如有）

#### 6. 交互说明
- 页面流程图（文字描述）
- 关键交互逻辑
- 边界条件处理
- 空状态/错误状态/加载状态的处理

#### 7. 数据需求
- 需要采集的数据字段
- 数据埋点方案
- 报表/看板需求

#### 8. 非功能需求
- 性能要求（响应时间、并发量）
- 兼容性要求
- 安全要求
- 可用性要求

#### 9. 验收标准
- 每个功能点对应 1-3 条验收标准
- 格式：在【条件】下，执行【操作】，预期【结果】
- 覆盖正常流程和异常流程

#### 10. 排期建议
- 设计：X 天
- 开发：X 天
- 测试：X 天
- 上线：X 天

### 第三步：输出规范
- 使用 Markdown 格式
- 表格优先于纯文字描述
- 复杂流程用文字版流程图表示
- 每个功能点编号，方便评审时引用
- 总篇幅控制在 3000-5000 字

### 第四步：质量检查
- [ ] 需求背景是否说清了"为什么做"
- [ ] 需求目标是否可衡量
- [ ] 用户故事是否覆盖主要场景
- [ ] 每个功能是否有明确的输入输出
- [ ] 异常处理是否完整
- [ ] 验收标准是否可测试
- [ ] 非功能需求是否考虑周全
- [ ] 非目标是否明确

## 示例

**用户输入：** 我们要做一个用户反馈功能，让用户可以在 App 内提交反馈

**输出（节选）：**

### 需求背景
当前用户反馈需通过邮件提交，链路长、回复慢，用户满意度低。竞品均已在 App 内提供反馈入口，响应时长缩短 60%。

### 需求目标
1. 用户可在 App 内一键提交反馈，提交率提升至 15%
2. 平均反馈响应时长从 48h 缩短至 12h
3. 收集结构化反馈数据，支撑产品迭代决策

### 非目标
- 不做反馈的实时聊天功能（本期）
- 不做反馈的公开社区展示（本期）

### 用户故事
1. 作为普通用户，我希望在 App 内找到反馈入口，以便快速提交问题
2. 作为普通用户，我希望可以附带截图，以便更准确描述问题
3. 作为产品经理，我希望看到反馈数据看板，以便分析用户痛点分布
